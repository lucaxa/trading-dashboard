A9 — PRODUCTION-BOUNDARY CAPTURE SPECIFICATION

Research architecture specification.

RESEARCH ONLY — NO PRODUCTION MODIFICATION AUTHORIZED

1. Purpose

A7 established the Opportunity Event Capture Contract.

A8 validated that the event model can replay historical observations
without treating heartbeat observations as independent opportunities.

Historical Phase 11 evidence does not contain the original
production-created opportunity identity.

Therefore historical replay can only infer identity.

A9 defines where the authoritative opportunity identity must be created
in the future.

2. Architectural Principle

Opportunity identity must be created when a genuine executable signal
event is generated.

It must be created before downstream lifecycle blocking.

Required architecture:

SIGNAL GENERATION
       |
       v
OPPORTUNITY EVENT CREATION
       |
       +-- opportunityId
       +-- signalEventId
       +-- signalTimestamp
       +-- signalCandleTimestamp
       |
       v
HEARTBEAT OBSERVATIONS
       |
       v
QUALIFICATION
       |
       v
PRIORITIZATION
       |
       v
LIFECYCLE
       |
       v
OUTCOME

A lifecycle-blocked opportunity must already possess an identity.

The system must not wait until after lifecycle processing to create the
opportunity record.

3. Capture Boundary

The capture boundary is the actual strategy signal-generation boundary
where a new executable BUY or SELL event is produced.

The required ordering is:

SIGNAL GENERATED
       |
       v
CREATE OPPORTUNITY
       |
       v
QUALIFICATION
       |
       v
PRIORITIZATION
       |
       v
LIFECYCLE DECISION

The following architecture is forbidden:

SIGNAL GENERATED
       |
       v
LIFECYCLE
       |
       v
CREATE OPPORTUNITY

The second arrangement would cause lifecycle-blocked opportunities to
disappear from the opportunity population.

A9 therefore establishes that opportunity creation precedes lifecycle
blocking.

4. Executable Signals

Initial executable signals remain:

BUY

SELL

WAIT is not an executable opportunity.

A WAIT observation must:

not create an opportunityId

not create a signalEventId

not increment an opportunity sequence

remain observable when included in the evidence stream

WAIT may terminate an active executable signal stream according to the
actual signal-generation behavior.

5. Opportunity Identity

Every newly created executable opportunity must contain:

opportunityId

signalEventId

instrument

timeframe

sessionDate

signal

signalTimestamp

signalCandleTimestamp

The identity must be created exactly once.

The identity must remain immutable for the opportunity lifecycle.

6. Opportunity ID Requirements

The production opportunityId must:

be created exactly once

be immutable

be unique within its required identity scope

remain associated with all subsequent observations

be independent of outcome

be independent of profitability

be independent of future candles

be independent of lifecycle acceptance

be independent of P&L

not be regenerated by heartbeat observations

If a random identifier is used, the immutable event fields must still be
preserved so deterministic research replay remains possible.

The preferred architecture is an identity derived from immutable event
attributes or an immutable identifier accompanied by sufficient
replayable event fields.

7. Signal Event ID

signalEventId identifies the signal-generation event.

It must be created at the same boundary as opportunityId.

It must not change because:

price changes

context changes

entry changes

stop changes

target changes

confidence changes

lifecycle state changes

outcome changes

The relationship is:

ONE SIGNAL EVENT
       |
       v
ONE OPPORTUNITY IDENTITY
       |
       +-- MANY OBSERVATIONS

8. Signal Timestamp

signalTimestamp records the timestamp at which the executable signal
event is generated.

It is distinct from:

heartbeat observation timestamp

entry timestamp

lifecycle timestamp

outcome timestamp

signalTimestamp must never be overwritten by a later observation.

9. Signal Candle Timestamp

signalCandleTimestamp identifies the completed 5-minute market candle
associated with the executable signal event.

It must represent the source market candle.

It must not be replaced by the timestamp of a later heartbeat.

The architecture must preserve these concepts independently:

observationTimestamp
signalTimestamp
signalCandleTimestamp

They may contain equal values only when they genuinely represent the
same source event.

The exact source of signalCandleTimestamp must be audited before any
production implementation.

10. Event Creation Rule

A new opportunity event is eligible for creation when:

signal is BUY or SELL

the signal represents a genuine new executable event

signalTimestamp is valid

signalCandleTimestamp is valid

instrument is available

timeframe is available

sessionDate is available

Once the event is created:

opportunityId = IMMUTABLE
signalEventId = IMMUTABLE
signalTimestamp = IMMUTABLE
signalCandleTimestamp = IMMUTABLE

Later observations cannot rewrite these fields.

11. Heartbeat Rule

Subsequent observations belonging to the same opportunity must
reference the existing opportunityId and signalEventId.

Heartbeat observations may update observable state such as:

price

trend

momentum

volatility

confidence

buyScore

sellScore

entry

stop

target

ATR

strategy status

These changes must not independently create another opportunity.

Required relationship:

OPPORTUNITY-001
      |
      +-- Observation 1
      +-- Observation 2
      +-- Observation 3
      +-- Observation N

12. Observation Sequence

Every observation belonging to an opportunity must have a monotonically
increasing observationSequence.

Example:

opportunityId = OPP-001

observationSequence:

1
2
3
4
...

A heartbeat must not reset the sequence.

A new opportunity starts a new sequence.

Duplicate observations must not create a second identity or silently
reset the sequence.

13. Signal Transition Rule

An executable signal transition may create a new opportunity when the
actual signal-generation boundary identifies a new executable event.

Examples:

BUY  -> SELL
SELL -> BUY
WAIT -> BUY
WAIT -> SELL

A transition from BUY or SELL to WAIT ends the current executable
signal stream.

The exact production transition semantics must be audited against the
existing V10.25 signal-generation behavior before implementation.

A9 does not select or modify those signal-generation rules.

14. Context Changes

Changes in market context do not independently create new
opportunities.

Examples include:

trend

momentum

volatility

confidence

buyScore

sellScore

VWAP relationship

These changes remain observations of the existing opportunity unless
the actual signal-generation boundary explicitly creates a new
executable event.

Therefore:

CONTEXT CHANGE
      !=
NEW OPPORTUNITY

15. Execution-Level Changes

Changes to:

entry

stop

target

risk

ATR

do not independently create new opportunities.

They remain state observations attached to the existing opportunity.

Therefore:

ENTRY CHANGE
STOP CHANGE
TARGET CHANGE
ATR CHANGE
      |
      v
UPDATED OBSERVATION
      |
      !=
NEW OPPORTUNITY

16. Qualification Relationship

Qualification is downstream from opportunity creation.

Required ordering:

OPPORTUNITY CREATED
       |
       v
QUALIFICATION

Qualification may classify an opportunity as:

NOT_EVALUATED

QUALIFIED

NOT_QUALIFIED

INSUFFICIENT_CONTEXT

Qualification must not redefine opportunity identity.

A qualification result must not be used retrospectively to decide
whether the opportunity existed.

17. Prioritization Relationship

Prioritization is downstream from opportunity creation and
qualification.

Required ordering:

OPPORTUNITY
       |
       v
QUALIFICATION
       |
       v
PRIORITIZATION

Ranking must not create or destroy opportunity identity.

Ranking must not use future outcomes or profitability as identity
inputs.

18. Lifecycle Relationship

Lifecycle remains downstream.

Required architecture:

OPPORTUNITY
       |
       v
QUALIFICATION
       |
       v
PRIORITIZATION
       |
       v
LIFECYCLE

A lifecycle block must never delete the opportunity.

A lifecycle block must preserve:

opportunityId

signalEventId

signal identity

market context

provenance

lifecycle state

lifecycle reason

Therefore:

LIFECYCLE BLOCK
      !=
OPPORTUNITY INVALIDITY

19. Outcome Relationship

Outcome occurs after lifecycle.

Outcome must never participate in opportunity creation.

The following are forbidden as identity inputs:

TARGET

STOP

SESSION_CLOSE

R multiple

P&L

future price movement

future market context

future indicator values

Counterfactual outcomes remain research-only.

The architectural relationship is:

OPPORTUNITY
      |
      v
LIFECYCLE
      |
      v
OUTCOME

and never:

OUTCOME
   |
   v
OPPORTUNITY IDENTITY

21. Provenance

Each opportunity must preserve enough provenance to reproduce its
origin.

Required provenance includes:

source

sourceVersion

evidenceVersion

creationTimestamp

signalTimestamp

signalCandleTimestamp

Where available:

evidenceFile

candleFile

Provenance must remain associated with the opportunity even when
lifecycle blocks it.

22. Historical Limitation

Current historical Phase 11 evidence does not contain the original
production-created opportunityId or authoritative
signalCandleTimestamp.

Therefore:

Historical replay identity
        =
Inferred research identity

It must NOT be represented as:

Historical replay identity
        =
Original production identity

A8 therefore validates the event architecture mechanically, but does
not prove that its reconstructed identifiers were the identifiers used
by V10.25 at the original signal-generation boundary.

This limitation must remain explicitly documented.

23. Validation Requirements

Before production implementation, the capture design must be validated
against the existing signal-generation behavior.

Validation must prove:

BUY events can be identified.

SELL events can be identified.

WAIT does not create opportunities.

Heartbeats attach to existing opportunities.

Context changes do not create duplicate opportunities.

Entry/stop/target changes do not create duplicate opportunities.

Signal transitions create the correct boundaries.

Identity remains immutable.

Observation sequence remains monotonic.

Outcomes do not influence identity.

Profitability does not influence identity.

Future information does not influence identity.

Provenance is preserved.

Lifecycle remains downstream.

Restart behavior does not incorrectly duplicate identity.

Session boundaries are handled correctly.

Duplicate event creation is prevented.

Safety boundaries remain enforced.

29. Architectural Conclusion

A9 establishes the required architectural boundary between signal
generation and downstream lifecycle handling.

The central decision is:

CREATE OPPORTUNITY IDENTITY AT THE ACTUAL EXECUTABLE
SIGNAL-GENERATION BOUNDARY, BEFORE LIFECYCLE BLOCKING.

This ensures that an opportunity exists independently of whether the
lifecycle later accepts or blocks it.

The architecture therefore preserves:

SIGNAL EVENT
      !=
HEARTBEAT OBSERVATION
      !=
OPPORTUNITY IDENTITY
      !=
LIFECYCLE DECISION
      !=
TRADE OUTCOME

A7 established this separation conceptually.

A8 validated the separation through historical replay.

A9 defines the required origin of authoritative identity for future
evidence.
